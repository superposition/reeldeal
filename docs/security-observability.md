# Demo security and observability boundary

ReelDeal is a demo, not a production-ready fishery or payment system. The static browser is untrusted: it can capture facts, run Laya or the local stub, and request actions, but cannot approve a Lot, verify its own bid signature, or confirm its own chain anchor. The Bun API must validate with the [shared contract](contracts.md), apply the [gate](../packages/domain/src/gate.ts) and state machines, verify signed bids, and commit state plus audit atomically. A reported Laya hash identifies the artifact the browser claims to have loaded; it is **not** remote attestation or fish-quality validation.

## Organization, role, and actor boundary

| Principal | Allowed demo action and attribution | Boundary still missing |
| --- | --- | --- |
| Seller organization/operator | Owns scans, Lots and Listings; a named operator supplies species and requests review. The [review route](../apps/api/src/routes/review.ts) checks a submitted active operator/seller row in the Lot's org. Accept/pay require a server-only `REELDEAL_SELLER_TOKEN` and audit `system:demo-seller-operator`. | The scanner accepts an operator label, the [observation route](../apps/api/src/routes/observations.ts) uses a fixed demo org and `device:browser-scanner`, publish has no seller credential, and review trusts a submitted `actor_id` after a role lookup. The accept/pay token authorizes a demo action, **not** an authenticated seller session or a verified human identity. Cross-org authorization and role sessions are absent. |
| Capture device | Takes a real photo and submits one stable `scan_id`; audit uses `actor_kind:device` and a device ID distinct from a human reviewer. | A browser label is not a hardware credential. Do not treat it as proof of who held the camera. |
| Buyer wallet | Signs one EIP-712 bid with amount, listing, address and nonce; the [bid route](../apps/api/src/routes/bids.ts) verifies the signer before insert. The internal audit row uses `actor_kind:wallet` and the signer address. | The signature proves that bid statement, not a login session, inventory reservation, or payment. Buyer identity access controls need production design. A deterministic public wallet alias, when served, is pseudonymization rather than anonymity; the full signer remains in SQLite. |
| API/system | Recomputes gate, performs legal transitions, verifies chain receipts, records retries and failures; audit uses `actor_kind:system` with a service ID. | The [anchor mutation](../apps/api/src/routes/provenance.ts) uses a server-side operator token and fails closed when absent. Do not place that token, RPC credentials, or private keys in Git or browser bundles. |

The append-only [audit table](../apps/api/src/db/schema.sql) is the durable internal record: `id`, `entity_type`, `entity_id`, `org_id`, `actor_kind`, `actor_id`, `from_status`, `to_status`, `request_id`, `payload_json`, and `at`. `GET /v1/audit?entity=&id=` returns newest-first events with those fields, parsed `payload`, and `at_iso`. At main `20a87d4`, the public route returns wallet actor IDs and payload values unchanged; the privacy follow-up must project deterministic wallet aliases and omit buyer-link IDs from the **public response** while retaining full attribution in SQLite. Do not describe aliases as anonymous or resistant to all re-identification. Material state transitions and meaningful failed attempts (such as a second bid acceptance) need audit events. An immutable TypedDecision links to its Observation and stores model ID/version/runtime, reported pinned weights SHA-256 when Laya, confidence/source, latency, and typed answer; its audit payload includes `reported_model` and `evidence_trust:client_reported_unverified`. A human Correction records the original field value (column `model_value`), human value, reason, and actor without editing the original Observation or Decision.

## Telemetry contract and current status

| Signal | Concrete name / fields | What it can honestly say |
| --- | --- | --- |
| Request log | JSON line `event:http_request` with `at`, `request_id`, method, route **template**, status, `duration_ms`, outcome; echo `x-request-id`. | [index.ts](../apps/api/src/index.ts) wraps all route handlers. This correlates an HTTP request but is not a distributed trace. Never log query strings, bodies, authorization headers, raw images, or bid signatures. |
| Audit query | `GET /v1/audit?entity=&id=`; fields above, actor kind taken from the stored row. | The [route](../apps/api/src/routes/audit.ts) is implemented and shows durable transitions and attribution claims. Public projection/redaction remains a privacy gate; no audit row proves that a browser ran a specific model. |
| Durable counters | `GET /v1/metrics`: `scans`, `decisions_per_backend` keyed by `model_id`, `review_rate:{reviewed_lots,total_lots,ratio|null}`, `anchors:{pending,confirmed}`. | Implemented from persisted server facts. `ratio:null` when there are no Lots; no fabricated denominator. These are demo counters, not production SLOs. |
| Browser-only counters | `model_inferences:null`, `weight_cache_hits:null`, with reason codes in `unavailable`. | No server measurement exists until browser events are explicitly reported, attributable and stored. Never present zero as observed activity. |
| Correlation / tracing | `request_id` in request log and audit row; linked scan, Observation, Decision, Lot, Bid and Sale IDs. | Entity links support manual reconstruction, but not every route propagates the wrapper's `x-request-id` into its audit row; a single cross-service trace ID is **not** proven. No exporter, spans, sampling policy, or external alert service is deployed. |

The [observation route](../apps/api/src/routes/observations.ts) audits scan creation once and each new immutable Observation; exact replay adds neither row. Decision, Lot/publish, review, bid, accept/pay, and [provenance](../apps/api/src/routes/provenance.ts) routes audit their implemented material transitions. The competing-accept conflict records a separate Listing attempt event; malformed or rejected bid requests do not all have audit rows. Retry identity is `scan_id` for observations, pinned observation/decision IDs for decisions, `(listing_id,nonce)` for bids, and stored payload hash for chain anchoring. Failures must retain a recoverable original fact and may not return success for an uncommitted write.

## Failure classes and accountable owner

These are escalation owners for the demo, **not** configured automatic alerts or an on-call rotation. RD-24 and the deployment owner must connect real notifications before production use.

| Failure class / detection | First owner | Required response |
| --- | --- | --- |
| API/SQLite unavailable, failed write, or missing audit event; health failure or request `5xx` | API operator | Stop claiming durability, inspect transaction and restore storage; replay only with stable IDs. |
| Laya manifest/hash/runtime failure, stub fallback, inference timeout, or browser cache failure; visible worker error | Decision operator | Fail closed to identified stub or review, retain Observation, record backend/fallback reason; never present heuristic confidence as calibrated fish accuracy. |
| Pending anchor, RPC timeout, or receipt/hash mismatch; pending/failed record | Chain operator | Preserve payload hash and attempt history, verify receipt before `confirmed`, retry without broadcasting a different payload. |
| Signature mismatch, nonce-replay spike, contested second accept, or missing seller token; `401`/`409`/`503` and audit outcomes | Marketplace/security operator | Reject mutation, keep one winner, inspect actor/nonce and audit trail without exposing the token. Do not treat a wallet signature as settlement. |
| Unexpected public image or buyer-identity disclosure; public response inspection or report | Marketplace/security operator | Stop using real data, restrict the affected read path, preserve audit evidence, and coordinate a documented purge; aliases alone are not access control. |
| Static Pages/API origin unreachable or cross-origin browser failure; page cannot save/retrieve | Deploy operator | Show degraded state, check public API origin and CORS, restore service; never display a build-time listing as live stock. |

## Sensitive data and retention

Treat landing photos, measurements, prices, bid signatures, buyer wallet/user links, and sale records as sensitive demo data. The scanner sends a JPEG data URL in `image_ref` and the API stores it in SQLite. On main `20a87d4`, public Listing/Lot/Observation reads can return that image, and public audit events expose buyer wallet IDs and bid amounts; the proposed alias/redaction follow-up narrows the public audit response but does not make a wallet anonymous. There is no application-layer encryption, automatic expiry, deletion workflow, or fine-grained access control for these reads. Use only synthetic or explicitly consenting demo data and test wallets with no funds; never put private fishery photos or customer identities into this public demo. Restrict database and backup access, keep secrets out of logs and Git, and arrange a manual post-demo purge with the data owner. Production use needs consent, retention/deletion periods, access control, public-response minimization, encryption, and incident response first.

## Design acceptance and runtime gates

The [audit tests](../apps/api/test/audit.test.ts) verify stored user/device attribution, filters, non-secret request logs, durable counters, and explicitly unavailable browser counters. Decision, review, bid, and sale tests cover their own transition/audit contracts. On main `20a87d4`, `bun run smoke:local` passed the complete disposable demo path, including one accepted and one conflicting bid acceptance with two Listing attempt audits. This supports the design and implemented demo telemetry, **not** production readiness. Before wider use, verify the public alias projection, close image/identity access and retention gaps, propagate a consistent request ID, add real alert delivery, and playtest human capture/scale and wallet paths. A browser-reported model run and a recorded `tx_hash` remain unverified evidence, never a quality or payment claim.
