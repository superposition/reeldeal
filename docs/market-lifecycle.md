# Marketplace lifecycle: one lot, one sale

The [domain/API contract](contracts.md) defines the v1 wire surface; [machines.ts](../packages/domain/src/machines.ts) defines legal state changes. This is a demo market: JPY amounts are display denominations and `Payment.captured` means a recorded demo settlement, not a charge, transfer, or verified chain payment.

## Actor and state path

| Action and actor | State changes | Required boundary |
| --- | --- | --- |
| Publish, seller intent | Approved Lot `approved → listed`; new Listing `open` | [Lot route](../apps/api/src/routes/lots.ts) rejects `pending_review` with `409` and its gate reason. The listing copies the Lot seller organization and price. A scan cannot directly create a listing. The current publish route has no authenticated seller session and audits a system actor. |
| Discover, buyer | No state change | The [marketplace](../apps/web/src/pages/shop/index.astro) lists published inventory; Lot detail must show effective facts, status, typed decision, corrections, and audit trail. A static Pages shell is not a live stock snapshot; query the API for current records. |
| Bid, buyer wallet | New Bid `placed`; Listing stays `open` | Buyer signs the shared [EIP-712 Bid shape](../packages/domain/src/bid.ts): `listing_id`, `amount_jpy`, `bidder`, `nonce`, under `ReelDeal` v1 and configured `chainId`. API verifies the signature before insert. Bad signature is `401 signature_mismatch`; reused `(listing_id,nonce)` is `409 nonce_reused` by the [unique index](../apps/api/src/db/schema.sql). Bidding on a non-open listing is `409`. A signature authorizes a bid, **not** a sale or general login. |
| Accept, demo seller operator | Winning Bid `placed → winning → accepted`; Listing `open → accepted`; Lot `listed → reserved`; new Sale `agreed` and Payment `quoted`; losing placed Bids `outbid` | A server-only `REELDEAL_SELLER_TOKEN` bearer token authorizes this demo action. Missing configuration fails closed with `503`; missing/wrong token returns `401` without a write. It is **not** an authenticated seller session or cross-org role check. The API checks current Listing/Lot/Bid status and commits transitions plus audits in one immediate SQLite transaction. A buyer cannot reserve stock by bidding alone. |
| Record demo settlement, demo seller operator | Sale `agreed → paid`; Payment `quoted → captured`; Lot `reserved → sold`; Listing `accepted → settled` | `POST /v1/sales/:id/pay` requires the same server-only token and a syntactically valid `0x`-prefixed 64-hex `tx_hash`, then records the reference and transitions together. The response and audit mark it `demo:true, verification:'unverified'`. Neither the reference nor the recorded states prove an on-chain receipt or real payment. |
| Cancel while open, seller | Listing `open → cancelled`; Lot `listed → withdrawn`; each still-placed Bid `placed → rejected` | Cancellation must be atomic, include a reason and audit entries, and prevent future bids/accepts. Buyer-initiated withdrawal may move **only that buyer's** `placed → withdrawn` bid while the listing remains open. An accepted/reserved listing cannot be cancelled through v1; it needs a separately designed compensating workflow. |

There is **no automatic expiry** in the v1 schema or API: no `expires_at`, scheduler, or timed transition. The defined policy ends an open listing by seller cancellation or acceptance, and lets a buyer withdraw only their own placed bid. Because cancellation and withdrawal routes are not yet shipped, the current runtime can only advance an open listing through acceptance. The UI must not show a countdown or imply timed release. `bid_received`, `payment_pending`, refund, and dispute are not v1 states.

## Single-winner inventory rule

`POST /v1/listings/:id/accept` serializes competing requests around one open Listing and listed Lot with an immediate SQLite transaction and rechecks state inside it. The [schema](../apps/api/src/db/schema.sql) also has `UNIQUE sales.listing_id` and `UNIQUE listings.lot_id` as final guards. If two bids are accepted concurrently, exactly one request returns `201 {sale}`. The second returns `409` naming the persisted `winning_bid_id`; it creates no second Sale and cannot move a reserved Lot backward. Both attempts leave Listing audit entries: an accepted transition and a conflict outcome with no status change. A retry after acceptance is a conflict, not a second success.

The append-only [audit log contract](contracts.md#shared-conventions) applies to implemented publish, bid, accept and pay actions, and must also cover cancellation/withdrawal if those routes ship. It records actor, original and next status, request ID, timestamp, and outcome; mutations and their audit rows commit together. Preserve signed bid bytes, nonce, and accepted Sale links. Do not rewrite earlier bids, sale, or payment history to make a cancellation or correction look as though it never happened.

## Delivery boundary and verification

Lot/Listing publish and detail, [signed bids](../apps/api/src/routes/bids.ts), and [accept/pay](../apps/api/src/routes/sales.ts) are implemented on main at `20a87d4`. The bid signature is verified before insert and `(listing_id,nonce)` is unique. The accept/pay routes use the token above and audit every successful transition; they do not establish a seller identity. Cancellation and bid withdrawal remain **defined policy only**, with no v1 routes or UI; an accepted/reserved listing has no compensating cancellation workflow. No automatic expiry or actual payment verification is implemented.

`bun run smoke:local` starts a loopback API with a disposable SQLite database and an in-memory demo seller token. It passed two signed offers, tampered amount `401`, nonce replay `409`, concurrent acceptance `201 + 409` naming the same winner, two Listing acceptance-attempt audit rows, one Sale, and demo settlement to `captured / sold / settled` with an **unverified synthetic** reference; a second pay returned `409`. Plain [smoke.sh](../scripts/smoke.sh) deliberately skips accept/pay when no seller token is supplied. The design state and conflict policy can be reviewed independently of remaining runtime gates: a human second-wallet playtest, cancellation/withdrawal implementation if advertised, and any real payment or authenticated seller claim.
