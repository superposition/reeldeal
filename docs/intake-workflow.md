# Dockside intake and review

This is the demo path from a physical landing to an approved Lot. The [domain/API contract](contracts.md) defines the wire fields and transitions; the [decision pipeline](decision-pipeline.md) defines typed answers and the review policy. A photo and operator-entered measurements are evidence, not proof that a model recognizes or grades fish. Laya is out of distribution for fish; species remains an operator-confirmed fact.

## Landing to Lot

| Step | FishScan state and actor | Durable fact or guard |
| --- | --- | --- |
| Capture | `captured` on the device; capture API moves it to `observed` | The browser assigns a UUID `scan_id` before upload. The operator takes a real camera photo, enters known length/weight, and may label and confirm species. Unknown values stay `null`; a manually entered weight is **not** a stable scale reading. `POST /v1/observations` creates the scan and its first immutable Observation together. |
| Decide | `observed → decided`, decision API | Browser Laya or the deterministic stub produces a validated TypedDecision tied to the exact `observation_id`; the API stores it, but does not run Laya. A changed observation needs a new decision. The binary `noul:false` completeness answer means required facts are missing, not model abstention. |
| Gate | `decided → promoted`, system, **or** `decided → reviewed`, human-review queue | Server recomputes the [pure gate](../packages/domain/src/gate.ts) from persisted facts. Auto approval requires positive length/weight, a stable agreeing scale reading, an operator-confirmed species with a non-conflicting candidate, and decision confidence at least `0.80`. Missing facts, a false completeness answer, conflict, or lower confidence yield `pending_review` with a reason; `[0.60,0.80)` is the ordinary uncertainty band. No gate result is a fish-quality accuracy claim. |
| Review | `reviewed → promoted | discarded`, named human reviewer | The operator sees the original value, reason, and model/policy source. A correction appends `field`, server-derived `model_value`, `human_value`, `reason`, and `actor_id`; it never edits the Observation or TypedDecision. The effective Lot field is visibly human-supplied. Approval/correction and their audit events must commit in one transaction; rejection records `discarded`. |
| Lot | `draft → approved | pending_review`, gate; `pending_review → approved | withdrawn`, reviewer | The Lot pins `scan_id` and `decision_id`. A reviewer can approve a pending Lot after addressing the reason. Only an approved Lot can move to `listed`; `POST /v1/lots/:id/publish` must reject a pending Lot with `409` and the gate reason. No listing is created directly from a scan or an unapproved Lot. |

The legal transitions are executable in [machines.ts](../packages/domain/src/machines.ts). Each state change has an actor, timestamp, request ID, and append-only audit event. The demo's operator label is attribution, not production authentication.

## Duplicate submissions and interrupted capture

- Reuse the original `scan_id` for every retry, including after a timeout whose server outcome is unknown. The [observation route](../apps/api/src/routes/observations.ts) returns `200 {replayed:true}` for an exact repeat without another Observation or FishScan; changed facts under that ID append a new immutable Observation (`201 {replaced:true}`), never another FishScan. Scan creation is audited once. After reconnect, `GET /v1/observations/:scan_id` can distinguish a saved result from a request that never arrived.
- The [current scanner](../apps/web/src/components/Scanner.tsx) stores active/last scan IDs in `localStorage`, retains the captured photo and form values only while the page is open, and checks the saved observation on reload. If an upload times out while the page remains open, retry uses the same ID and photo. A successfully saved observation survives reload in the API.
- **Remaining offline gap:** an *unsent* photo and form do not survive reload, so the full "capture survives reload" acceptance criterion is not yet met. Before claiming offline intake, persist the unsent capture plus form and `scan_id` in browser-owned storage (for example IndexedDB), restore it on reload, retry with the same ID, and clear it only after server confirmation. If storage is unavailable, tell the operator capture is not durable; never claim an offline save.
- Camera permission denial leaves manual fields editable, but the current flow will not submit without a real photo. A missing `PUBLIC_API_ORIGIN` on a static deployment also disables saving. Neither case should silently create a scan.

## Current enforcement and proof boundary

The scanner and observation persistence above are implemented. The [decision](../apps/api/src/routes/decisions.ts) and [Lot/review/publish](../apps/api/src/routes/lots.ts) API routes are still `501` placeholders at this revision. [RD-17](https://github.com/superposition/reeldeal/issues/21) owns the review UI, [RD-18](https://github.com/superposition/reeldeal/issues/22) owns the server-side Lot/listing guard, and [RD-28](https://github.com/superposition/reeldeal/issues/34) owns submission verification. The pure gate and machines are not substitutes for route-level enforcement.

The [smoke script](../scripts/smoke.sh) currently checks only API health. This ticket's verification remains open until it also runs both transactional paths: (1) complete, eligible observation → decision → approved Lot → listing; (2) `weight_g:null` → review → attributed correction/approval → Lot, with publish rejected before approval. The happy path must inspect persisted rows and audit events; the review path must prove the original observation/decision remain unchanged. Do not close the [intake epic](https://github.com/superposition/reeldeal/issues/5) or report end-to-end acceptance from a health-only smoke pass.
