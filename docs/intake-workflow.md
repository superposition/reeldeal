# Dockside intake and review

This is the demo path from a physical landing to an approved Lot. The [domain/API contract](contracts.md) defines the wire fields and transitions; the [decision pipeline](decision-pipeline.md) defines typed answers and the review policy. A photo and operator-entered measurements are evidence, not proof that a model recognizes or grades fish. Laya is out of distribution for fish; species remains an operator-confirmed fact.

## Landing to Lot

| Step | FishScan state and actor | Durable fact or guard |
| --- | --- | --- |
| Capture | `captured` on the device; capture API moves it to `observed` | The browser assigns a UUID `scan_id` before upload. The operator takes a real camera photo, enters known length/weight, and may label and confirm species. Unknown values stay `null`; a manually entered weight is **not** a stable scale reading. `POST /v1/observations` creates the scan and its first immutable Observation together. |
| Decide | `observed → decided`, decision API | Browser Laya or the deterministic stub produces a validated TypedDecision tied to the exact `observation_id`; the API stores it, but does not run Laya. A changed observation needs a new decision. The binary `noul:false` completeness answer means required facts are missing, not model abstention. |
| Gate | `decided → promoted` on auto approval; a pending-review scan stays `decided` | Server recomputes the [pure gate](../packages/domain/src/gate.ts) from persisted facts. Auto approval requires positive length/weight, a stable agreeing scale reading, an operator-confirmed species with a non-conflicting candidate, and decision confidence at least `0.80`. Missing facts, a false completeness answer, conflict, or lower confidence yield a `pending_review` Lot with a reason; `[0.60,0.80)` is the ordinary uncertainty band. No gate result is a fish-quality accuracy claim. |
| Review | `decided → reviewed → promoted`, named human reviewer | The reviewer sees the original fact, reason, and reported model/policy source. A correction appends `field`, `model_value`, `human_value`, `reason`, and `actor_id`; the column named `model_value` holds the original recorded field value, **not** a fish measurement inferred by Laya. The Observation and TypedDecision remain unchanged, and the effective Lot field is visibly human-supplied. Correction, approval, and their audit events commit in one transaction. `reviewed → discarded` is defined in the state machine but has no rejection route yet. |
| Lot | `draft → approved | pending_review`, gate; `pending_review → approved | withdrawn`, reviewer | The Lot pins `scan_id` and `decision_id`. A reviewer can approve a pending Lot after addressing the reason. Only an approved Lot can move to `listed`; `POST /v1/lots/:id/publish` must reject a pending Lot with `409` and the gate reason. No listing is created directly from a scan or an unapproved Lot. |

The legal transitions are executable in [machines.ts](../packages/domain/src/machines.ts). Implemented state changes have an actor, timestamp, request ID, and append-only audit event. The review route checks that the submitted `actor_id` names an active operator or seller in the Lot's organization, but has no authenticated caller session; the demo operator label is attribution, not proof of identity.

## Duplicate submissions and interrupted capture

- Reuse the original `scan_id` for every retry, including after a timeout whose server outcome is unknown. The [observation route](../apps/api/src/routes/observations.ts) returns `200 {replayed:true}` for an exact repeat without another Observation or FishScan; changed facts under that ID append a new immutable Observation (`201 {replaced:true}`), never another FishScan. Scan creation is audited once. After reconnect, `GET /v1/observations/:scan_id` can distinguish a saved result from a request that never arrived.
- The [scanner](../apps/web/src/components/Scanner.tsx) stores one bounded local draft: JPEG photo, capture timestamp, `scan_id`, and entered facts. Reload restores it without opening the camera or uploading anything. Saving is explicit and retries the original ID and facts, including when an earlier request reached the server but its response was lost. A local draft is not evidence that the server has or has not saved it.
- Browser storage holds at most 2,000,000 serialized characters for this draft. A confirmed save or **New landing** clears it. Oversize, quota, denied-storage and failed-clear states warn the operator rather than claiming durable storage; keep the page open or clear site storage as directed. This is device-local recovery, not a background synchronization queue, an offline page-install guarantee, or private encrypted storage. A successfully saved observation survives reload in the API.
- Camera permission denial leaves manual fields editable, but the current flow will not submit without a real photo. A missing `PUBLIC_API_ORIGIN` on a static deployment also disables saving. Neither case should silently create a scan.

## Current enforcement and proof boundary

The scanner, [observation](../apps/api/src/routes/observations.ts), [decision](../apps/api/src/routes/decisions.ts), [Lot/review/publish](../apps/api/src/routes/lots.ts) APIs, and review UI are implemented. [postPublish](../apps/api/src/routes/lot-service.ts) rejects a `pending_review` Lot with `409 review_required` and its gate reason; a Listing is inserted only after an `approved → listed` Lot transition in the same transaction. The decision API validates and stores the browser's reported evidence, but cannot attest that Laya actually ran. A manual weight in the scanner has `scale_reading.stable:false`, so it routes to review until a human correction attests the missing scale facts. The separate `/v1/scans/:id/corrections` draft endpoint remains `501`; `/v1/lots/:id/review` is the implemented correction path.

`bun run smoke:local` uses a disposable SQLite database and passes the eligible Observation → Decision → approved Lot → Listing path and the `weight_g:null` → `pending_review` → publish `409 (noul)` path. [Review tests](../apps/api/src/routes/review.test.ts) prove that attributed correction/approval preserves the original Observation and TypedDecision and audits the scan/Lot transitions. A separate synthetic browser playtest covers two corrections, explicit publication and reload; the shell smoke does **not** itself exercise that human correction.

The synthetic-camera browser test also covers capture → local reload → dropped save response → reload → exact retry: one Observation for the scan, followed by draft clearing and no resurrection after New landing. It uses a visibly labeled canvas stream, not a physical camera. A real camera/scale playtest, authenticated operator/device identity, and a rejection/discard endpoint remain runtime gaps. Local draft recovery does not claim that a cold offline page load or a real device has been tested.
